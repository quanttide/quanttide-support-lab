量潮客户支持 · 领域模型

核心模型只有一个关系：一次问题的提出与解答（Ticket），蒸馏为沉淀下来的可复用知识（Solution）。

Ticket 工单 × Solution 解决方案

两个实体

Ticket 工单 · 对齐 GitHub Issue

一次客户问题的提出与解答。一问多答 = issue + comments，没有独立的 Reply 实体。

iduuid
number仓库内递增编号，对外引用用 #192
title / body问题标题与详情（Markdown）
stateopen | closed，无"已解决"中间态
author / labels提交者；轻量标签（faq / bug / feature-request）
comments时间序交流流，客户 / 支持 / ai 同流发言
created_at / closed_at提出 / 关闭时间

Solution 解决方案

从已 closed 的 Ticket 蒸馏创建，不允许凭空出现——每条知识都有真实案例背书。

iduuid
title"什么问题"一句话
content解答本体（Markdown），来源引用写在开头；失效走归档不删除
适用场景 / 解答 / 升级判据 / 来源与复用 —— 是 content 的推荐写法，不是模型字段。

知识从实例中长出

循环埋在 Ticket 与 Solution 的关系里，是模型结构本身，不是口号。

1
问题进来

客户提问形成 Ticket，open，评论流开始。

2
解答并关闭

支持人员 / AI 在评论流中应答，解答完成即 closed。

3
蒸馏为 Solution

从已 closed 的 Ticket 蒸馏知识，来源引用写进 content 开头。

4
复用加速

后续同类问题由 AI 直接参考 Solution 应答，更快、更少升级。

建模思想

  1. 领域只说业务语言模型里只有 Ticket 和 Solution。语义检索、存储引擎、LLM 供应商都是技术选型，归应用层——换个技术栈，模型原样成立。
  2. 两个字段哲学：问答与知识业务抽象到底只有两个动作：回答问题（Ticket）、积累知识（Solution）。状态、优先级、分派、统计都是派生需求。
  3. 知识从实例中长出Solution 不允许凭空创建。解答 Ticket → 蒸馏 Solution → 参考复用 → 更多问题被更快解答，循环是模型结构本身。
  4. 格式沿用成熟惯例Ticket 对齐 GitHub Issue，语义已被千万开发者验证：一问多答就是评论流，状态就是 open/closed，引用就是 #number。目标是零学习成本。
  5. 模型与档案互为镜像qtcloud-support 是模型的可部署实现，档案仓库是人可维护的形态。两者一一对应、双向同步，数据不属于任何一个端。
